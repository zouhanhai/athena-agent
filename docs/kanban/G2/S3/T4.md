# G2.S3.T4: Retrieval Verification

## Task

End-to-end verification of the knowledge access layer + Pi retrieval routing.

## Implementation

### 1. Dual-Pipeline Ingest Test
- Ingest a sample document (via T2 /api/kb/ingest)
- Confirm present in LightRAG (query returns relevant chunk) + llm_wiki (file appears in tree + searchable)

### 2. Pi End-to-End Retrieval
- Through Pi AgentSession, ask:
  - Process/standards question → should use wiki_search (llm_wiki)
  - Fact/semantic question → should use knowledge_search (LightRAG)
  - Relationship question → should use query_graph / wiki_graph
  - Cross-domain complex question → multi-source fusion
- Verify Pi picks correct tool + returns coherent answer

### 3. Report
- Document verification results in ticket Log
- Note any routing issues + fixes

### 3. Findings / notes
- Tool-call observation uses the `tool_execution_start` session event (carries `toolName`); the `tool_call` event is extension-only and never reaches `AgentSession.subscribe` listeners.
- Within a single session Pi correctly skips re-querying once the answer is already in conversation context (per design §3.3 "simple/chit-chat → answer directly"); verification therefore uses a fresh agent per intent to isolate routing.
- Added `tools?: string[]` allowlist to `CreateAgentOptions` (→ `createAgentSession`) to restrict a session to the knowledge tools for deterministic routing tests.
- One transient OpenRouter stream stall seen mid-run (retry succeeded) — network flakiness on `openrouter.ai`, not a code issue.
