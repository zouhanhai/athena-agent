# G2.S5.T11: Wiki Tree View Switcher (Single Storage + Segmented Control)

## Problem

After T10 (topic grouping), each Sommerseminar doc appears TWICE in the wiki tree:
once under `concepts/` (by type) and once under `sommerseminar/` (by topic). This is
duplicate storage — violates knowledge-base best practice (a doc lives in ONE place;
multi-dimensional classification uses metadata, not file copies).

## Solution (industry best practice)

**Single physical storage + frontend view switching.** Store each page once (with
frontmatter `type` + `topic` metadata); the frontend tree groups dynamically by the
selected view — no file duplication.

## UI Design

Segmented control in the Wiki header (left of the Refresh button), TDesign `t-radio-group`
with `t-radio-button` (button variant) to render an iOS-style segmented control:

```
Wiki    [ ⊞ Topic | ◫ Type | ≡ All ]   🔄
```

| View | Groups by |
|------|-----------|
| Topic | `wiki/<topic>/` (e.g. sommerseminar/, project-x/) — default, most useful |
| Type  | `wiki/<category>/` (concepts/, entities/, sources/) |
| All   | raw physical directory tree |

## Dark / Light theme adaptation (MUST)

- Use `--caleo-*` CSS variables (`--caleo-surface`, `--caleo-border`, `--caleo-text`,
  `--caleo-text-secondary`, brand orange) — same pattern as the rest of WikiView.
- Selected segment = CALEO brand orange (`#ff6633`); unselected = surface/text-secondary.
- Must look correct in BOTH `mode: "dark"` and `mode: "light"` (via `useThemeStore`).
- Test manually in both themes (toggle in Settings).

## Implementation

1. Backend: ensure wiki tree API returns each page's `type` + `topic` metadata (read from
   page frontmatter) so the frontend can group by either dimension. Do NOT duplicate files.
2. Frontend `web/src/views/WikiView.vue`:
   - Add `view` ref (`"topic" | "type" | "all"`, default `"topic"`)
   - Add segmented control in `wiki-controls`
   - Compute tree from the single metadata list per the active view
   - Keep active page selected across view switches when possible
3. Unit tests for view switching logic.
4. Remove existing duplicate files (re-ingest so each doc has one canonical file with
   frontmatter `type` + `topic`).
