# G3.S5.T5: Show source images in llm_wiki pages (pure-text for LightRAG)

## Goal (user's words)

When reading an .md file in **llm_wiki**, it should show **both the text AND the original document images**,
at the same relative position as in the original — like viewing the source file but as Markdown.
Meanwhile **LightRAG must be unaffected**: it should still see **pure text** (the VLM description docling
generates), NOT image references/bytes.

In short: the current `<image>` placeholder becomes a **link to a stored image file** so that when the
md is opened in llm_wiki the image auto-loads and displays; but LightRAG still sees the plain-text file.

## Architecture (already favourable — confirm, don't break)

Current ingest flow (server/src/kb/ingest.ts `ingestMarkdown`):
- docling parses source → markdown containing `![<VLM description>](images/xxx.png)` (image ref + alt text)
- `ingestLlmWiki(fileName, content)` writes the **full markdown** to `wiki/<topic>/<name>.md` (line 486)
  → llm_wiki reads this file; it will render images **if the image files sit beside it**
- `ingestLightRag(frontmatterContent)` sends the same markdown to LightRAG → LightRAG stores **text only**
  (image refs collapse to the `![alt]` text = the VLM description) → chunking unaffected ✅

So the split is already correct. The gap is ONLY the **image files**: docling doesn't save them because
`docling.ts` `parse()` calls parse_doc.py **without `--images-dir`**.

## Implementation

1. `server/src/kb/docling.ts` `parse()`: append `--images-dir <outDir>/images/<stem>` to the parse_doc.py
   argv; return the images dir in `DoclingParseResult`.
2. `server/src/kb/ingest.ts` `ingestLlmWiki` (and the task-queue path in `tasks.ts`): after writing the
   wiki page, **copy the extracted image files into the same target dir** (`wiki/<topic>/images/`) and,
   if needed, rewrite the markdown image refs so they resolve relative to the page. The wiki page's
   frontmatter/content is unchanged apart from the image path normalization.
3. `server/src/routes/kb.ts`: add `GET /api/kb/wiki/image?path=` (same `isSafeWikiPath` style guard) that
   streams the image bytes from the wiki dir. Update `web/src/views/WikiView.vue` so `renderMarkdown`
   output rewrites `<img src="images/...">` → `<img src="/api/kb/wiki/image?path=<resolved>">`.
4. Do NOT touch the LightRAG path — it already gets pure text. Add a test asserting LightRAG content has
   no image refs (or only alt text) while the wiki file keeps them.
5. Tests: docling returns images dir; images copied beside wiki page; wiki image route serves bytes;
   frontend image src rewritten to the served URL; LightRAG content remains text-only.
