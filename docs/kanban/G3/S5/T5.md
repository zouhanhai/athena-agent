# G3.S5.T5: Preserve extracted images in wiki pages — save image files + VLM description, viewable in llm_wiki

## Task

When docling parses a document, it currently **drops the image bytes** — images become VLM-generated
alt-text descriptions (good for RAG search) but the actual picture is lost. We want **both**:
the picture saved as a file **and** referenced in the markdown so it renders in the llm_wiki reader,
while the VLM description keeps the content searchable.

`parse_doc.py` already supports this: `--images-dir <dir>` + `export_to_markdown(image_export_dir=...)`
writes extracted images and references them in the markdown. The gap is the **backend**:
`docling.ts` `parse()` calls parse_doc.py **without `--images-dir`** (server/src/kb/docling.ts:87),
so images are never written.

## Implementation

1. Backend `docling.ts`: pass `--images-dir` to parse_doc.py (e.g. `~/athena-data/input/images/<stem>/`),
   return the images dir in `DoclingParseResult`.
2. `ingest.ts` (llm_wiki stage) / `tasks.ts`: **copy the extracted images into the wiki dir**
   next to the page (e.g. `wiki/<topic>/images/`), and rewrite the markdown image refs to relative
   paths that resolve there. So when llm_wiki reads the page, the images are beside it.
3. Serving: images must be reachable by the frontend. Add a route (e.g. `GET /api/kb/wiki/image?path=`
   with the same safety check as `readWikiPage`) that reads the image bytes from the wiki dir, OR
   serve the wiki dir statically. Update `WikiView` `renderMarkdown` to rewrite image srcs to the
   served URL.
4. Keep VLM descriptions: `PictureDescriptionApiOptions` stays on so the alt-text/description is
   preserved in the markdown alongside the `![alt](images/...png)` reference.
5. Tests: docling parse returns images dir; images copied into wiki dir; wiki image route serves bytes;
   frontend renders an image tag with the served URL.
