# G3.S2.T4: Invitation-based employee registration

## Task

Invitation email → magic-link → registration page (link email, fill profile + GitHub key).

## Implementation

- Invite: send invitation email (Resend) with invite token
- Registration page: link own email (verify), fill display name + logo + GitHub key/token
- Store encrypted GitHub credential
- Login via magic-link

## Log

- `server/src/employees/invitations.ts` — `InvitationService`: `invite(email)` creates a
  single-use invite token + emails the registration link via `InvitationMailer`
  (`ResendInvitationMailer` when `RESEND_API_KEY`, `ConsoleInvitationMailer` in dev);
  `resolveInvitation(token)` returns the invited email (registration page; non-consuming);
  `registerInvitedEmployee(token, input)` consumes the token, creates the employee (role member,
  display_name + logo_url + encrypted GitHub credential) and mints a session token so the new
  employee is signed in immediately. Existing-employee invites → `InvitationConflictError` /
  `EmployeeConflictError`; invalid/expired tokens → `InvitationInvalidError`.
  `MemoryInvitationStore` + `PostgresInvitationStore` (`auth_invitations`, invite tokens stored as
  SHA-256 hashes only, 7-day TTL).
- `server/src/employees/rbac.ts` — new `employees.invite` permission (admin-only).
- `server/src/routes/invitations.ts` — `POST /api/invitations` (admin RBAC `employees.invite`,
  `{ email }` → 201 | 400 | 409), `GET /api/invitations/resolve?token=` (public → `{ email }` | 401),
  `POST /api/invitations/register` (`{ token, display_name?, logo_url?, github_credential? }`
  → 201 `{ session_token, employee }` | 400 | 401 | 409). GitHub credential validated + stored
  encrypted at rest (reuses T2 SecretCipher + registry).
- `server/src/app.ts` — shared `AuthTokenStore` between auth + invitation services so a
  registration-time session resolves through the auth service; `defaultInvitationService`
  (Postgres when `DATABASE_URL`, else memory); `buildApp` wires `registerInvitationRoutes` and
  closes the invitation store + token pool on shutdown.
- `web/src/api/invitations.ts` — `resolveInvitation`, `registerInvitedEmployee`, `sendInvite`,
  `requestMagicLink`, `verifyMagicLink`, `fetchMe` (Bearer `/api/me`).
- `web/src/stores/auth.ts` — Pinia auth store: session token persisted in localStorage
  (`athena.session_token`), `isAuthenticated`, `setSession` (login verify or registration),
  `setEmployee`, `bootstrap` (re-hydrate via GET /api/me on app load), `logout`.
- `web/src/views/RegisterView.vue` — `/register?token=` registration page: resolves the invite
  (the emailed magic-link token verifies ownership of the invited email — see §4.4 "associates
  their own email"), then employee fills display name + logo picker (owl + S1 generated set) +
  optional GitHub key/token; submit → POST /api/invitations/register → auto-login → /chat.
- `web/src/views/LoginView.vue` + `web/src/views/AuthVerifyView.vue` — magic-link login UI
  (request link → verify token → session → /chat).
- `web/src/App.vue` + `web/src/router/index.ts` — auth bootstrap on mount; /register, /login,
  /auth/verify routes.
