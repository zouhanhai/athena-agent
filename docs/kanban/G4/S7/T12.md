## Context

Yesterday we added per-user chat persistence (`chat_messages`, G4.S7.T11-followup): every
message is saved per employee and the frontend restores the WHOLE conversation on load.

Now the user wants a **session switcher** like Hermes TUI's `/resume`:
- Each user keeps up to **10 recent chat sessions** to pick from.
- Picking one resumes that conversation (loads its messages).
- A "New chat" action starts a fresh empty conversation.
- The picker UI goes in the **agent-card area** of the chat panel (the region where agent
  participant cards live), not a separate modal.

This is a schema + API + frontend feature on top of the existing chat_messages table.

## Task

### A. DB / store (`server/src/agents/chat-history.ts` + migration)

1. Add `session_id` column to `chat_messages` (TEXT, default '' for legacy rows — migration:
   lazy additive ALTER like the rest of the codebase; legacy rows with ''=today's flat history
   may be treated as one legacy session or excluded from the picker, pick one and document).
2. New table `chat_sessions` (or a session row per session_id):
   - `session_id TEXT PRIMARY KEY`
   - `employee_id TEXT NOT NULL`
   - `title TEXT` (derived: first user message or "New chat"), maybe `created_at`, `updated_at`
   - Indexed for per-employee ordering by updated_at DESC.
3. Store methods:
   - `createSession(userId, title?) -> session_id`
   - `listSessions(userId, limit=10) -> { session_id, title, created_at, updated_at, message_count }[]`
   - `ensureSession(userId, sessionId) -> session exists`
   - `touchSession(userId, sessionId)` called when a message lands so updated_at refreshes
   - `saveMessage` gains `sessionId` (message row carries it)
   - `listMessages(userId, sessionId?, limit)` — when sessionId is given, filter to that session.
4. DB migration: keep lazy-CREATE + additive-ALTER pattern, idempotent, safe on existing DBs.

### B. Server routes (`server/src/routes/chat.ts`)

1. `GET /api/chat/sessions?userId=` → `{ sessions: [...] }` (max 10, most recent first).
2. `POST /api/chat` body gains optional `session_id`:
   - When absent → server creates a NEW session automatically (new conversation).
   - When present → messages persist under that session; 404/400 if the session does not
     belong to the user (or auto-create if you prefer — pick + document).
3. `GET /api/chat/history?userId=&sessionId=` → messages ONLY for that session.
4. Persisted turns carry session_id (both the user and assistant rows).

### C. Frontend (`web/src/stores/chat.ts`, `api/chat.ts`, GlobalChatPanel.vue)

1. Store state:
   - `sessions: ChatSession[]` (10 recent), `activeSessionId: string | null`.
   - `loadSessions()` action → GET /api/chat/sessions → fills the list (no message fetch).
   - `pickSession(id)` → set active, GET /api/chat/history?sessionId= → restore messages.
   - `newChat()` → clear messages, clear activeSessionId, create session on server (or lazily
     on first message), then the first message opens a new session.
   - `send()` passes `session_id` (or omits it when starting fresh) — align with server.
2. **UI placement**: the picker + new-chat live in the AGENT-CARD AREA of the chat panel
   (the region where participant cards are rendered, e.g. top of the participant list /
   next to the agent cards). A compact session dropdown/menu: recent 10 with title + relative
   time + message count, plus "New chat" item. Keep it visually consistent with the existing
   card styling (same component family, not a global sidebar).
3. Initial load: after sign-in, load sessions list (cheap) but do NOT auto-restore the last
   session's messages unless the UI already did (decide: start at "New chat" empty state by
   default, or restore most recent — mirror Hermes /resume which shows the list and lets the
   user pick; do NOT block the chat on a fetch of a full 200-message conversation).

### D. Tests

- Store: session create/list/touch; messages carry session_id; listMessages filters by
  session; legacy ''-session rows don't break listing.
- Route: GET sessions (most recent 10, capped); POST /api/chat with session_id persists under
  the session + touch updates updated_at; without session_id → new session created; GET
  history?sessionId filters.
- Web: store loadSessions/pickSession/newChat wiring; UI presence in the agent-card area
  (chat.spec / shallow DOM test).

## Acceptance

1. A user with messages across multiple sessions sees their 10 most recent in the picker
   (server test asserts ordering + count cap).
2. POST with session_id lands in that session's history and its updated_at refreshes; without
   it a fresh session_id is created (tests assert).
3. Frontend picker renders in the agent-card area; picking a session restores ONLY that
   session's messages; New chat starts empty.
4. `npm test` green on 6900XT + web vitest green; `npx tsc --noEmit` clean.
