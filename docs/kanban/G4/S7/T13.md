## Context (empirical, 2026-08-26)

Today the Athena chat produced repeated EMPTY assistant replies that never hit OpenRouter
(0 token usage on the provider dashboard) while the turn took ~106s server-side:

1. The `wiki_read_page` tool returned an uncapped 2.4MB page → the tool result was persisted
   INTO the employee's single Pi session file (2.86MB jsonl, one 2,440,389-char line).
2. Every later turn resumed that session → prompt construction blew up instantly → empty
   reply persisted at t+12ms. Frontend showed "typing..." forever while the input box was
   already unlocked (state desync).
3. Fix applied on 6900XT: surgical repair of the poisoned jsonl (backup kept) + commit
   `c7642ce` caps `wiki_read_page` output at 48K chars.

Investigation surfaced the ROOT design gap (this ticket): the frontend "chat session"
(G4.S7.T12) is purely a DB grouping over messages, but the backend ignores it —
`AgentManager.getAgent(userId)` uses `SessionManager.continueRecent(...)`, i.e. ONE Pi
thread per USER forever. Consequences observed today:

- A "New chat" in the UI did NOT start a clean backend context; the poisoned thread kept
  producing empty replies regardless of which frontend session was used.
- Context leaks across frontend sessions (what you discuss in session A influences B).

## Task

1. **Thread-per-(user, sessionId)**: plumb the frontend `sessionId` through
   `routes/chat.ts` → `AgentManager.getAgent(userId)` → session selection. Key the
   AgentManager map and the Pi SessionManager dir/file scheme so each frontend session
   resolves to its own Pi thread. Concurrency note: keep the Map-keyed single-flight
   behavior per (userId, sessionId).
2. **Persistence-boundary truncation**: when appending any tool result / message into the
   Pi session file or `chat_messages.progress`, enforce the same 48K-char cap as
   `c7642ce` centrally (one shared constant/helper), so a future uncapped tool cannot
   poison a session again.
3. **Lifecycle**: hook new-session cleanup into the existing 10-session pruner — when a
   frontend session is deleted/pruned, its Pi thread file is removed too.
4. **Migration**: for pre-existing frontend sessions without a Pi-thread mapping,
   document the chosen default (recommended: lazily bind to the legacy thread on first
   message to preserve continuity, new sessions get clean threads).
5. **Guardrail test**: simulate a >1MB tool result injected mid-conversation; assert the
   OTHER sessions of the same user still answer normally (containment).

## Notes

- Do not change the MCP tools themselves here; the cap belongs at the persistence
  boundary (defense-in-depth behind `c7642ce`).
- Keep G4.S7.T12 API surface unchanged; this is server-internal wiring.
