## Context

S7's AgentIDE vision: users manage remote agents from the platform. Each agent stays local; the platform
is the control plane. For the platform to control an agent it needs to know the agent's identity +
reachability. **The capability model ALREADY exists**: `AgentCapabilities` (system/mcp[]/tools[]/skills[]/
specialty/description) + `POST /api/agents/self-declare` (agent self-declares capabilities) + employee
review/register (`POST /api/agents`). This ticket **extends** it with remote reachability (api_url/token)
via **invitation-based onboarding** (mirrors employee invites, and Avernet's registration/discovery/
invitation + capability profiles — see `docs/avernet-reference.md`). DO NOT rebuild a capability system —
it exists; just add the remote fields + invite flow.

## Task

1. **DB schema + model**: extend AgentRecord/`agents` table with remote fields: `api_url`, `token`,
   `agent_id` (unique). Migration for existing rows (nullable / defaults). Capability fields stay as-is.
2. **Invitation flow**: admin endpoint to generate an invite `{agent_id, api_url, token}`; a
   register/accept endpoint where the agent posts its api_url + token (auth'd) and the platform records
   reachability + status. Capabilities are still declared via the existing self-declare/register.
3. **Extend POST /api/agents + web Register form** (G3.S2.T9) to carry the remote/api_url/token fields.
4. **Agent identity + discovery**: each agent unique id + token; platform stores location + reachability;
   UI shows agent status (registered / reachable / unknown) + its capability profile (already stored).
5. **Tests**: server + web for the invitation flow + remote fields.

## Acceptance

- AgentRecord/schema has api_url/token/agent_id; existing manual register carries them.
- Invitation flow works: admin generates invite, agent registers auth'd, platform records reachability.
- Agent identity traceable. Tests green, typecheck clean.
