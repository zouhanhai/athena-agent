## Context

Remote agents (T4) receive each chat turn as an isolated `task` — the server currently sends only
`[page injection?] + the new user message` (`remote-chat.ts`). The remote agent explicitly confirmed
this: every task contains a single user message with **no history**, so long multi-turn
conversations are impossible.

Required behavior (user decision, 2026-08-17): the chat UI should accumulate the full conversation,
send the accumulated history with each task to the remote agent, AND monitor context size so that
when it reaches a threshold the server automatically summarizes older messages (LLM) and truncates
them before pushing. Token budgets are real: DeepSeek v4 Flash has a 1M-token window but remote
agents may have tighter limits; history grows linearly with turns, so unbounded accumulation is not
acceptable.

Architecture decisions (already agreed — implement as specified):

- **History lives on the chat client (`web/src/stores/chat.ts` `messages` array ✓ exists)** and is
  sent with every chat request as `history: {role, content}[]` (filter out system messages and
  empty-content assistant placeholders).
- **The server is the single authority for truncation/summarization** (it holds the full history at
  request time and is the only place with an LLM channel). Remote agent is NOT responsible for
  summarizing — it is stateless per task.
- **Summarization cost**: only when history exceeds the threshold. Below the threshold, pass history
  through unchanged (no extra LLM calls).
- **UI**: a context meter in the chat panel showing estimated tokens / threshold, so the user sees
  accumulation and the auto-summary trigger point.

## Task

### A. Server: history + context module (new file `server/src/agents/chat-context.ts`)

1. `estimateTokens(text: string): number` — documented heuristic: `Math.ceil(charLength / 4)` for
   ASCII-dominated text and `charLength`-ish for CJK (simple heuristic, no tokenizer; document the
   assumption and don't over-engineer).
2. `buildTaskMessages(history: ChatTurn[], message: string, pageInjection: string | undefined,
   opts: { thresholdTokens: number; recentMaxTurns: number; summarizer: Summarizer }): ChatTurn[]`
   — returns the messages array to push to a remote agent:
   - If `estimateTokens(history + message) <= thresholdTokens` → `[pageInjection?] + history + new user message`.
   - Else → produce a system summary of the OLD part (messages before `recentMaxTurns` recent turns)
     via the injected `summarizer`, and return `[pageInjection?] + {role:system, content:"Earlier
     conversation summary: ..."} + recent turns + new user message`.
   - Never drop the current message; never summarize the most recent `recentMaxTurns` turns verbatim
     (they are the live window).
3. `Summarizer` type: `(turns: ChatTurn[]) => Promise<string>` — injectable for tests. Production
   implementation can reuse the existing LLM seam pattern (see `server/src/kb/agentic-llm.ts`
   `AGENTIC_PROVIDER`/`AGENTIC_MODEL`, `completeSimple`-style call). It is acceptable to make the
   production summarizer a lightweight direct OpenRouter call via the athena provider key; keep the
   seam injectable so tests never hit the network.
4. Export defaults: `DEFAULT_CONTEXT_THRESHOLD_TOKENS` (propose 40_000) and
   `DEFAULT_RECENT_MAX_TURNS` (propose 40).

### B. Server: wire history through the chat route

1. `ChatRequestBody` gains `history?: unknown` — array of `{role: "user"|"assistant"|"system", content: string}`.
2. Validate: accept any role, filter out empty content; cap at some max turns (e.g. 200) defensively.
3. `handleRemoteChat` + `pushRemoteChatTask`: accept the validated history, build task messages via
   the context module (with the LLM summarizer wired in server-side; keep it a no-op/short-circuited
   when summarizer not configured, e.g. unit tests).
4. Local (non-remote) chat path: leave as-is (local AgentSession already manages its own session
   history) — this ticket is remote-agent scoped. If trivial, do NOT change local behavior.

### C. Web: send history + context meter

1. `web/src/api/chat.ts` `streamChat`/`sendChat` gain a `history` param; `postChat` includes
   `body.history` when provided.
2. `web/src/stores/chat.ts` `send()` passes `this.messages` (filtered: only user/assistant with
   non-empty content) as history. For the remote path (`agent.agentId`) and local path both — sending
   history locally is harmless; server decides what to do.
3. Context meter UI in `GlobalChatPanel.vue`:
   - A small bar/indicator showing `estimateTokens(history) / threshold` (mirror the server heuristic
     in `web/src/utils/context.ts` or reuse via a shared constant — keep it simple, a rough estimate).
   - Visual states: normal (< 80%), warning (80–100%), summarizing (>= 100% → server will summarize).
   - Show the estimate text like `~12k / 40k tokens`.

3. Above threshold → server returns `[system summary] + recent window + current message`; summarizer

## Notes

- Thresholds (40_000 tokens / 40 turns) are proposals — keep them as exported constants so tuning is
  one-line. Do NOT make them env-configurable in this ticket (YAGNI; constants are enough).
- The remote agent's own memory/session_search is a free bonus for recall beyond truncation — do NOT
  rely on it; the server-side summary is the contract.
- Summarization failure (network/LLM error) must NOT drop the conversation or block the message:
  fall back to truncating without a summary (keep the most recent `recentMaxTurns` + a system note
  that earlier context was omitted). Never fail the chat request because summarization failed.
- See `docs/kanban/G4/S7/T4.md` for the WS task frame format (`messages: {role, content}[]` is the
  exact payload shape — unchanged by this ticket).
