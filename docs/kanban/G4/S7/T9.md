## Context

The agent lifecycle is invite → agent self-registers via the onboarding URL (T2) and declares its
capabilities (T3, A2A-aligned: system/mcp/tools/skills/specialty/tags/examples) → then an **owner
review** is needed. Today Settings shows a flat agent list and the capability declaration goes
through a separate DeclarationCard, but there is no single **agent detail view** where an owner can
review an agent's declared capabilities, confirm it, change its alias, or change its logo — and no
re-confirmation when capabilities change. This ticket closes that loop.

## Task

1. **Agent detail view** — clicking an agent row in Settings opens a detail view (inline panel or
   route) showing:
   - agent identity (alias, agent_id, status, owner, logo)
   - declared capabilities: system / mcp[] / tools[] / skills[] / specialty / tags[] / examples[]
     (A2A-aligned, from AgentCapabilities)
   - reachability (api_url if any, connected/last-seen from the reverse-WS hub, G4.S7.T4)
2. **Review + confirm** — the owner can confirm/approve the agent from the detail view. Pending
   declarations (self-declare, T3) are reviewable here (merge the DeclarationCard review into the
   detail view).
3. **Edit alias + logo** — the owner can change the agent's alias and logo from the detail view
   (PUT /api/agents/:alias — update alias + logo_url; logo picker reuses the existing logo options).
4. **Re-confirm on capability change** — editing capabilities (or an agent re-declaring) sets the
   agent back to a `pending review` state; the owner must confirm again. When confirmed, mark the
   capabilities as reviewed/approved.
5. **Tests** — server (detail data, confirm, edit alias/logo, re-confirm-on-change) + web
   (detail view renders capabilities, confirm action, edit alias/logo, pending-review state).

## Acceptance

- Capability change → pending review → owner re-confirms.
- Settings Agents list links to the detail view; loop is closed end-to-end.

## Notes

- Builds on the improved invite URL (onboarding_url, T2) + A2A capability format (T3).
- The existing DeclarationCard review can be merged into the detail view (single review surface).
- Reconfirm-on-change: an explicit state on the agent (e.g. `capabilities_pending_review`) OR a
  per-declaration flag; pick the cleaner model.
