## Context

Hermes (the platform's own agent runtime) replays FULL message history to the LLM on every turn:
assistant turns carry their `reasoning_content` (thinking) — required by DeepSeek/Kimi/MiMo
thinking mode or the API rejects the request with HTTP 400 — and tool-call turns carry the tool
calls + tool results. Storage keeps the full trace; the wire copy only drops *pure-thinking
turns* (thinking with no content and no tool call).

Athena's remote-chat pipeline (G4.S7.T10) instead sends ONLY the final assistant answer text
(`historyForRequest()` filters to `{role, content}`). Thinking and tool output are rendered in
the UI but dropped from history. The user asked to align Athena with Hermes: **carry the
thinking and tool output back**, because the remote agent also runs DeepSeek, and continuing a
conversation often depends on earlier reasoning the final answer alone does not capture.

Current gap: the WS protocol's `tool.completed` frame carries only `detail?` (a description),
NOT the tool's actual output content. `thinking` frames already exist and are streamed to the
frontend — so thinking accumulation is protocol-ready, tool output needs a new optional frame
field.

## Task

### A. WS protocol (server/src/ws/agent.ts)

1. **Thinking**: no new frame needed for receiving (`thinking` exists). The agent runtime should
   include thinking in the task reply it sends; if a remote agent emits thinking as part of
   `delta`/final text, the platform must still accept the current shape. Do NOT break existing
   frames. The relay already exposes `onThinking`; ensure the chat route can hand thinking back
   to the store (it already does).
2. **Tool output**: extend `tool.completed` with an OPTIONAL field carrying tool result content:
   - `{ type: "tool.completed"; task_id; tool; detail?; status?: "ok"|"error"; error?; output?: string }`
   - `output` = the tool's returned content (terminal stdout, file excerpt, API response, etc.),
     when the remote agent can send it. MUST be optional: old connectors that send only detail
     still work, and the platform never fails because output is absent.
   - Add a test asserting an old-style `tool.completed` (no output) still relays fine.
3. **Update the self-describing taskReply contract** (registered frame): document that tool
   events may carry `output` and thinking is relayed — keep `protocolVersion: 1` (additive).

### B. Server wiring (chat-context.ts / remote-chat.ts / routes/chat.ts)

1. `ChatTurn` gains optional `thinking?: string` and `toolOutput?`-carrying shape. Keep
   `{role, content}` compatible (old history from pre-T11 clients is still accepted).
2. `est.registerTokens`/`estimateTokens` in `chat-context.ts`: when computing the history budget,
   INCLUDE thinking and tool output text (they are now part of history and consume budget).
3. `buildTaskMessages` passes thinking/tool output through to the messages array sent to the
   remote agent. The messages array keeps the standard shape Hermes expects:
   - assistant turn: `{ role: "assistant", content: <final text>, reasoning_content/thinking? }`
   - tool turn: `{ role: "tool", tool_call_id/name, content: <output> }`
   The REMOTE agent (Hermes API server) remains responsible for provider-specific handling
   (e.g., DeepSeek reasoning_content echo-back); Athena only delivers the data.
   Do NOT attempt to strip/pad reasoning_content (that's the agent's job).
4. Failure tolerance: missing thinking / missing tool output → history just omits it. Never fail.

### C. Frontend (web/src/stores/chat.ts, api/chat.ts, GlobalChatPanel.vue)

1. `ChatMessage` already has `thinking?` and `progress[]` (tool rows). Extend the message shape
   to also carry tool OUTPUT per tool event (e.g. `progress[i].output?` or a new field), filled
   from the WS relay for remote agents.
2. `historyForRequest()` now includes, per assistant turn:
   - `content` (final answer, as today)
   - `thinking` (the accumulated reasoning text for that turn)
   - per-tool `output` (the tool result content streamed back)
   Keep system messages filtered; keep empty placeholders filtered.
3. `GlobalChatPanel.vue` context meter: continue to estimate from the *full* history incl.
   thinking + tool output (the server does the same), so the meter and server threshold agree.
4. Keep the UI rendering unchanged in spirit: thinking block + tool progress rows already render.

### D. Tests

- Server: `ws/agent.ts` test — `tool.completed` with `output` relays output; without output
  still relays (old agent compat). `chat-context.test.ts` — budget includes thinking/tool
  output; passthrough and summarize paths still work with the extended ChatTurn shape.
- Server route: history carrying thinking/tool output is accepted and forwarded into the task
  payload.
- Web: chat.spec — `historyForRequest` includes thinking + tool output; meter reflects them.

4. No failure path when thinking/output missing.

## Notes

- Think of this as "deliver thinking + tool output as DATA; the remote agent decides what to do
  with it" — Athena does NOT implement reasoning_content padding/stripping (that is the agent
  runtime's provider policy, exactly as Hermes' `message_sanitization` does on the agent side).
- The threshold (200K) stays as-is; including thinking/tool output makes each turn heavier, which
  is expected and desired — the meter/server will simply show a fuller budget.
- Relevant Hermes reference (agent-side): `agent/message_sanitization.py`
  `apply_reasoning_content_policy` + `agent/agent_runtime_helpers.py`
  `drop_thinking_only_and_merge_users` — understanding these explains why Athena only needs to
  DELIVER the fields, not transform them.
- Remember to push BOTH remotes (origin + caleo) and sync-github after touching docs.
- Remote-agent cooperation: the wts-agent connector must start sending `output` in
  `tool.completed` and thinking (if not already) for full value; the platform-side changes here
  are how the data is carried/stored/replayed. Flag this in the Progress Log when done.
