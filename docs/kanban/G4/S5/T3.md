## Context

T1/T2 built the **md → GitHub projection**. This ticket closes the loop: **GitHub → md**. Two parts:
(1) **bidirectional sync** — user-confirmed GitHub Project changes (e.g. a card dragged to a Status
column) sync BACK to the md ticket, with the change's origin recorded in md; (2) **feedback loop** —
the plan agent reads new Issue comments and proposes md updates (new/edited ticket/spec). md stays
authoritative on ambiguity; human keeps final authority. This is the feedback loop of the Greenfield
team-collaboration flow.

## Task

1. **Bidirectional status sync** (`server/src/kanban/github-feedback.ts`):
   - `pullProjectStatusChanges(github, credential, owner, repo, board, project)` — reads the Project
     items' Status field, compares to the md ticket status, and for any difference **writes the
     GitHub-derived status to the md ticket** (user-confirmed on GitHub).
   - **Record origin in md**: each applied GitHub change appends a `## GitHub sync` note (or a
     `synced_from: github <timestamp> <field> <old>→<new>` row in the Progress Log) so a human can tell
     the change came from GitHub.

2. **Feedback reader**:
   - `listIssueComments` (already on GitHubApi) + **dedup**: track seen comment IDs in a
     `docs/kanban/Gx/Sy/sync-state.json` (or a frontmatter field) so the plan agent only processes new
     comments.

3. **Plan-agent reconcile path**:
   - A function that presents new issue comments + the current md state to the plan agent and lets it
     propose md updates (new/edited ticket, new spec). The proposal is a **draft**, NOT applied
     silently. Reuse `planning.ts` (PlanInput → planGoal) for new Goal/Spec/Ticket generation.

4. **Conflict handling (md authoritative on ambiguity)**:
   - When a sync would be ambiguous/conflicting, do NOT write silently — surface a report (log or a
     `conflicts` list in the sync tool output) for the plan agent to reconcile. A GitHub-derived change
     is always marked in md. md never auto-loses on ambiguity.

5. **CLI extension** (`server/scripts/sync-github.ts`): add `pull <specRef>` (GitHub→md status sync) +
   `feedback <specRef>` (comments → proposal). Both no-auto-apply on conflict.

6. **Tests** (`server/test/kanban-github-sync.test.ts`): mock GitHub; assert (a) status pull writes
   the GitHub status to md with an origin marker, (b) comment dedup (seen vs new), (c) proposal
   generation via planning.ts, (d) conflicting/ambiguous sync never silently overwrites md (a report
   is produced instead). Server tests green + typecheck clean.

## Acceptance

- Proposals are drafts, not silent writes.
