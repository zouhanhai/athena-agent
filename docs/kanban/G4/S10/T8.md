## Context

Diagnosed 2026-09-11 on 6900XT while restarting the backend (new pid 136154). The weekly KB
audit's missed-window catch-up ran at boot and aborted:

    [kb-audit] scheduled audit failed: wiki dir could not be resolved

`kb_audit_runs` has NO successful scheduled run since 2026-08-24 23:54 (scanned 6, changed 0).
Every audit run that needed to APPLY a change has failed since. Root cause, reproduced with a
probe:

**The deployment runs with `LLM_WIKI_WIKI_DIR` unset — by design.** The comment on the wiki-edit
syncer in `server/src/app.ts` ("LLM_WIKI_WIKI_DIR is not set in deployments — resolve the wiki dir
lazily through the ingest project lookup instead") plus commit f205ec0 (2026-08-22, review-state
syncer fix) establish the pattern: services resolve the wiki dir via
`kbIngest.resolveProject().wikiDir`. The weekly-audit chain was never migrated — five sites still
read the env var only (grep-verified):

| Site | Construction | Effect in deployment |
|---|---|---|
| defaultReviewService() syncer | `server/src/app.ts` (~258): `new WikiFrontmatterSyncer({ wikiDir, driver })` | any review decision → syncer.update → `wiki-frontmatter.ts` (~207) THROWS "wiki dir could not be resolved" → the WHOLE scheduled audit aborts (this is the live failure) |
| defaultKbAuditService() wikiDir | `server/src/app.ts` (~551): `process.env.LLM_WIKI_WIKI_DIR \|\| undefined` | file re-check degrades to "wiki dir not configured"; orphan sweep scans 0 dirs |
| defaultReCurator() | `server/src/app.ts` (~272) | manual wiki re-topic → 500 (same throw) |
| defaultFeedbackService() syncer | `server/src/app.ts` (~284) | QA confidence write-through throws |
| retrieval frontmatter syncer | `server/src/app.ts` (~199 default factory + ~612 buildApp IIFE) | read_count write-through silently skipped ("best-effort" catch) → read_count NEVER increments → the review's "rarely read" deprecate signal is always 0 |

Already-dynamic reference wiring (copy this): `server/src/app.ts` ~381 and ~819 —
`resolveWikiDir: async () => (await kbIngest.resolveProject()).wikiDir`.

**Probe evidence** (temp scripts run from `server/` on 6900XT, since removed):

- `defaultReviewService().reviewAll({ dryRun: true })` → `scanned=7 changed=6`, all decisions
  `deprecate` (stale/rarely-read pages under `wiki/internal/events/...`, `wiki/sap/...`,
  `wiki/unclassified/...`).
- real `reviewAll({})` → `APPLY_ERR wiki dir could not be resolved`, stack:
  KbReviewService.applyDecision (`review.ts` ~426) → WikiFrontmatterSyncer.update → wikiRoot
  (`wiki-frontmatter.ts` ~207). Identical message to the boot failure.
- `defaultIngestService().resolveProject()` → `{id: "athena-wiki", wikiDir: "/home/hh/athena-data/wiki/wiki"}` —
  the lazy source works in this deployment; the pages exist on disk.

**Impact**: the weekly KB audit has been broken for any run needing a change (18 days, silent —
failed runs are not persisted, so the scheduler just retries on the next restart); 6 pages are
waiting to be deprecated; manual re-topic is broken; the read_count signal is dead. Since
LLM_WIKI_WIKI_DIR is unset in EVERY deployment (not just 6900XT), this is not a machine-local issue.

## Task

1. Introduce one shared lazy resolver in `buildApp` (e.g. a `resolveWikiDir` closure over the
   graph-wired `kbIngest` instance — same source as the ~819 site) and pass it to the five sites
   above. Mind construction order: `review` is built (~604) BEFORE `kbIngest` (~735) — hoist
   `kbIngest`, or give the default factories an optional `resolveWikiDir` parameter, or use a
   deferred reference; keep it typed.
2. Keep the env var as an OPTIONAL override with precedence (env set → use it; unset → project
   lookup). Do NOT "fix" this by exporting LLM_WIKI_WIKI_DIR in `.env.local` / `start-all.sh` —
   that hides the wiring gap and breaks when the llm_wiki project path moves (rejected shortcut).
3. Unit tests (server): resolver precedence (env set vs unset), the review apply path using the
   resolver (no throw), and one same-class site (recurator or feedback). RED first.
4. Verify on 6900XT: server suite green; restart athena-back via `scripts/start-all.sh` (never a
   manual bare `npx tsx watch` — the Postgres-registry env must stay intact); trigger the manual
   audit (admin endpoint) and confirm: persisted `kb_audit_runs` row, the 6 pending deprecations
   applied, `scannedDirs > 0`, no "wiki dir" errors in `~/.athena-tmp/athena-server.log`. Record
   before/after evidence for one page (frontmatter confidence + the audit row id).
5. Feature-level English commit(s); `codegraph sync`; push caleo first, then origin, BEFORE
   marking done.
