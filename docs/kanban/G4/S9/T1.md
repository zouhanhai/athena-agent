## Context

G4.S8 delivered a stable ingest/edit/delete graph (approved). G4.S9 spec section 1:
Leiden community detection over Entity+RELATION (optionally MENTIONED_IN co-weight).
The knowledge graph at fixture scale is ~20-50 entities; choose an implementation
that fits the stack (probably in-process JS/TS — no GDS server dependency) and a
strategy that stays fast at the planned scale (day-1 target: hundreds of documents,
thousands of entities).

## Task

1. Implement/reuse community detection:
   - Try `neo4j-graph-data-science` community edition availability for
     `gds.beta.community.leiden`; if the community container doesn't ship GDS or
     the license is awkward, implement in-process: read entities+relations via the
     driver, run a JS Leiden/Louvain, write `community_id` back with a batched
     `SET e.community_id = $id`.
   - Keep it deterministic (seeded) so fixtures are stable.
2. Incremental strategy:
   - delete/big-ingest → full re-run.
   - small wiki-edit diff → recompute for the changed entity's community +
     neighbours (heuristic; document limits).
   - size < threshold → always full re-run (simple and fine for our scale).
3. Tests + fixtures: synthetic small graph; then real ingest of the two Sommer docs
   and assert the CALEO-centric partition.

## Notes

- Community id should be stable when possible (a canonical member id or a hash of
  sorted members) so refreshes don't churn member nodes.
- Do NOT touch retrieval in this ticket (T3 owns the query path).
- Keep memberships as a property; a Community node with summary is T2's job.
