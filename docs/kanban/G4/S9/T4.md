## Context

Community detection (T1, approved) auto-maintains memberships incrementally on
ingest/edit/delete; community summaries (T2, in progress) give each community a
theme. The user wants a first-class Admin surface for the maintenance operations
that are NOT automatic: a manual full recompute (when a big batch of changes lands
or the user wants a fresh partition), plus community-quality visibility inside the
existing weekly audit (T15) rather than a separate periodic job.

## Task

1. **Admin endpoint**: `POST /api/kb/admin/communities/recompute` (admin-gated like
   the audit endpoints) → runs the full community re-run + T2 summaries update →
   returns a report `{ communities, entitiesPerCommunity[], largestCommunity, changedSinceLast }`
   → persisted into the audit-report history with `trigger: manual`.
2. **Weekly audit section**: extend the T15 audit report with a community-quality
   block (reusing the same report store, trigger: weekly): community count, size
   distribution, entities not in any community, community summaries (T2), and the
   orphan check already there. Distinguish manual vs weekly via trigger field as
   today.
3. **Admin UI**: in the existing admin maintenance/report area, a "Recompute
   communities" button + a table/history of community runs (trigger, time, counts).

## Acceptance

Per frontmatter. Non-admin must be rejected; manual trigger must appear in history.

## Notes

- Reuse T15's report store + admin-gate helper; do NOT create a second store.
- The recompute button should be non-blocking (fire task) with a 'running' state,
  or a quick sync path at current scale — implementer's call, document it.
- Community summary refresh reuses T2's summarizer (only changed communities).
