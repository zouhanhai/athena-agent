## Context (2026-08-21, user requirement + review finding)

User: “还要确认远程的 agent 能够知道如何提供这些信息，我们的 ws 是通过握手协议通知远程
agent 的，那这些关于将 code 上传知识库的协议如何操作”.

Current state (verified):

- The WS handshake `registered` frame self-describes how to REPLY to pushed tasks
  (`taskReply` contract, G4.S7.T4 — "no protocol guessing") but says NOTHING about how to
  SUBMIT intake. The upload endpoint (`POST /api/kb/ingest`, kinds cds/abap/ui5, ddic after
  T9) is discoverable only out-of-band (task prompt prose / human setup).
- The code-channel routes perform NO auth at all (only wiki-page save checks
  `currentEmployee`) — anyone can POST code into the KB.
- The KB MCP server (`/api/kb/mcp`) is the CONSUMPTION side (search/get_page/get_graph/
  get_topics/get_tree) for OpenCode/Claude-Code-class clients. Intake is the PRODUCTION
  side, served to WS-connected SAP agents. Mixing ingest into MCP would hand write access
  to every MCP token and blur the two roles — explicitly out of scope.

## Design

### 1. Intake contract in the handshake (ws/agent.ts)

Extend the `registered` frame payload:

```ts
intake: {
  channels: [
    {
      kind: "cds",                       // abap | ui5 | ddic — from the shared constant
      method: "POST",
      endpoint: "/api/kb/ingest",
      requiredFields: ["content"],
      optionalFields: ["filename", "system", "devclass", "transport"],
      returns: { taskId: "async ingest task id; poll GET /api/kb/task/:id" },
    },
    // ... one entry per channel
  ],
  auth: "Authorization: Bearer <agent token>",
}
```

Single source of truth: define `INTAKE_CHANNELS` once (e.g. in `ws/agent.ts` or a small
shared module) and derive BOTH the handshake payload and (structurally) the route
validation from it, so a future channel kind cannot forget the handshake entry.

### 2. Intake auth (routes/kb.ts)

The code-channel handlers currently skip auth. Add a shared pre-handler:

- `Authorization: Bearer <token>` — accept EITHER
  - an agent token: verify against the AgentRegistry (same invitation-hash credential the
    WS `register` frame validates — reuse its verification path), or
  - an employee session token (existing `currentEmployee` path — web UI keeps working).
- No/invalid token → 401. Apply to kinds cds/abap/ui5/ddic only (leave the existing
  employee-only routes as they are).

### 3. Non-goals

- No MCP changes (retrieval-only by design).
- No WS upload frames — HTTP POST with 202 + taskId is the right shape for large payloads
  and reuses the existing async task queue + progress polling.
