## Context (2026-08-21, user requirement)

The refine quality gate works (Lüsen ingest returned `action: review_required` with two
concrete issues: missing image captions, a `Zustieg am ?????` placeholder in the source),
but the user only sees a bare review-required badge — the ISSUES themselves are invisible
in the frontend. User requirement (verbatim intent): “要不是问了你，前端根本看不见要我
review 哪些点。如果需要复核的文件，应该把复核 msg 直接出现在 wiki 页面，悬浮或类似 PDF
标记写 comment 写在该审核的地方，让 user 可以修改和确认每一处。”

T16 provides the data: structured anchored issues
(`{ id, message, anchor: { quote, headingPath } | unresolved }`) persisted in
`quality.json` + `review: required` in the page frontmatter, served through the code-meta
API (T11).

## Design

### 1. Uploads view — issue details

Task detail (running + finished) renders the quality issues list: per issue the message
and heading path. A review-required task shows the badge WITH the expandable issue list.

### 2. WikiView — banner + inline annotations

- `review: required` pages render a banner above the content: "本页有 N 处需要复核" with
  a list of issues; anchored ones jump to their highlight on click, unanchored ones are
  listed in the banner only (their anchor quote no longer matches the content — likely
  edited since; never silently dropped).
- Inline annotations: after content render, for each anchored issue, find its
  `anchor.quote` (whitespace-normalized) in the rendered HTML text and wrap the match in
  a highlight element (mark.js or equivalent); clicking a highlight opens a TDesign
  popover with the issue message + two actions:
  - 确认无误 → resolve (persists per-issue state, banner count decrements)
  - 需要修改 → keeps the issue open, optionally attaches the user's note
- All issues resolved → banner disappears and frontmatter `review: clear` is written.

### 3. Persistence API

`POST /api/kb/wiki/review-state` (employee auth): body
`{ path, issueId, action: "resolve" | "reopen", note? }` → updates the issues array in
quality.json, recomputes `review`/`review_count` in the page frontmatter, and mirrors the
review status onto the Neo4j Document node via the existing frontmatter write-through
channel (T1's updateWikiFrontmatter convention).

### 4. Edge cases

- Page edited after review: anchors re-validated on each code-meta fetch; broken anchors
  degrade to banner-listed items (never lost).
- Pages without issues: no banner, no annotations (zero overhead).
- The scheduled weekly audit (T15) re-reviews pages; a new review_required run replaces
  the issue set (user-resolved state resets with the fresh review — documented behavior).
