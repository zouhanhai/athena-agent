## Context (2026-08-21, user requirement)

User: “SAP 系统的表结构是不是也得收录到知识库里” — YES. After T8, CDS/ABAP edges point at
bare table-NAME entities (e.g. `MARA` created only because a view reads it). Ingesting real
DDIC definitions upgrades those nodes into rich, field-level knowledge:

```
CDS view --READS_FROM--> MARA (bare name entity after T8)
DDIC intake:             MARA → header chunk + field chunks (KUNNR/BUKRS/... with data elements)
                         → "which field stores the customer number" becomes answerable
```

Master-data SEMANTICS (which tables compose customer master, business meaning) flows through
the normal docling/wiki channel — no new pipeline needed. Master-data RECORDS (actual rows)
are explicitly OUT of scope (volume/staleness/PII).

## Design

### 1. Wire format (what the remote SAP agent submits)

`POST /api/kb/ingest` with `kind: "ddic"`:

```json
{
  "kind": "ddic",
  "system": "prd",
  "devclass": "ZFI",
  "content": "[{ \"name\": \"MARA\", \"description\": \"General Material Data\",
                \"fields\": [{ \"name\": \"MATNR\", \"key\": true, \"dataType\": \"CHAR\",
                              \"dataElement\": \"MATNR\", \"domain\": \"MATNR\", \"description\": \"Material Number\" }],
                \"foreignKeys\": [{ \"field\": \"...", \"table\": \"T001\", \"description\": \"...\" }] }]"
}
```

The descriptor set is what an SAP-side MCP pull produces (DD02L/DD03L/DD04T read or
RFC `DDIF_FIELDINFO_GET`) — the platform does NOT call SAP; it only consumes this JSON.
Keep the parser tolerant: unknown extra fields ignored, missing `description` fine,
empty `fields` → header chunk only.

### 2. Parser (server/src/kb/codeparse/ddic.ts)

- `parseDdicTables(content: string): DdicTable[]` — validate + normalize the JSON array
  (throw a clear error listing the offending table index on malformed input).
- Chunking (deterministic): one header chunk per table (`path = <tableName>/_header`,
  text = name + description + key-field list) + one chunk per ~20 fields
  (`path = <tableName>/fields/<n>`), mirroring the code-channel chunk shapes
  (`RefinementChunk` with heading_path).

### 3. Store (server/src/kb/store/ddic.ts)

- `storeDdicOutput(tables, options)` mirroring `storeCodeOutput`: writes `chunks.json` +
  `markdown.md` (rendered table documentation: field tables in markdown), returns a
  `RefineOutputRef` with frontmatter `{ type: "code", topic: codeTopic(provenance) }`.
- Entities/relations: `Table` entity per table; foreign-key targets as entities +
  `REFERENCES` edges (external targets included — same MATCH-by-nameUpper rule as T8).

### 4. Pipeline + route

- `tasks.ts runDdic` mirroring `runCode` (same stage machine, same T8-style preclassified
  derivation from the ref); `taskQueue.submitDdic`; `routes/kb.ts` `kind === "ddic"` branch
  (copy the cds branch shape).
- Wiki page lands under `wiki/code/<system>/<table>.md` via the same preclassified flow.

### 5. Tests

Parser (valid/invalid/chunk-splitting), store façade (frontmatter/entities/relations),
route branch (202 + taskId), one pipeline smoke test. Full `npm test` green.
