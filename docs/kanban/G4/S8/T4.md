## Context (2026-08-20)

CALEO consultancy needs SAP source code in the KB (Q&A: "which method reads table A", "what does
ZCL_FI_GR_DELTA do", "which function module posts revenue lines"). ABAP is the second code source family
after CDS (T3). ABAP is text but NOT prose: boundaries are `CLASS ... ENDCLASS`, `METHOD ... ENDMETHOD`,
`FUNCTION ... ENDFUNCTION`, `FORM ... ENDFORM`, `REPORT`, `INCLUDE`. docling/markdown chunking is wrong
for it.

## Decision (from user discussion, 2026-08-20)

- Same direction as T3: **code channel** (direct text), local deterministic chunking, LLM for
  enrichment only.
- ABAP parsing is NOT regex — use **abaplint** (the standard open-source ABAP linter/parser, TS)
  to get a real AST and walk statements. This gives correct boundaries AND the ability to extract
  dependencies (table reads, CALL FUNCTION/FORM/METHOD, type refs) that feed the knowledge graph.
- Chunk text = the raw ABAP statement text for the unit (method body + signature); do NOT have the LLM
  rewrite code. GPT enrichment writes a summary/annotation separate from the chunk text (code stays
  verbatim — like T1's delta contract for prose).

## Design

### Intake

- Reuse the T3 code channel (task queue, dedup sha256 on normalized source, wiki/RAG/Neo4j storage).
- Source shape: a text payload per object (or concatenated objects with a header line
  `@object: <name> <type> <devclass>`); typically pulled from SAP ADT/MCP exports (e.g. `SAPRead`)
  or pasted. Add `kind="abap"` to the T3 ingest discriminator.
- No docling — the raw source goes directly to the parser.

### Remote acquisition (SAP side) — REQUIRED (2026-08-20 user note; same as T3)

ABAP objects live in the SAP system — the user does NOT upload them; a **remote agent pulls via the
abap MCP server** (already configured) and feeds athena:

**A. Pull side — SAP MCP (fetcher agent):**
- `SAPSearch` to find objects by package/devclass (e.g. `ZFI*`, `ZGR*`), `SAPRead` to fetch each
  object's source (class body, function module, report, include), `SAPQuery` optional for
  where-used/dependencies. The agent wraps each pull as
  `{ objectType, objectName, devclass, programName/include, sourceText, system, ts }`.
- ABAP specifics: object may be split across INCLUDEs — fetch main object + its includes (SAPRead
  supports include content), keep the include mapping in the chunk metadata so a method's body is
  findable even when it lives in an include.

**B. Feed side — athena intake:**
- Same `POST /api/kb/ingest/remote` (or `source=mcp`, `kind="abap"`) endpoint as T3: batch body of
  objects, machine-token auth (env `ATHENA_AGENT_TOKEN`), SHA-256 dedup + update-on-change, single
  ingest task, per-object storage with `system/devclass/transport` provenance in frontmatter.
- Periodic re-pull = sync: unchanged objects skipped, changed ones re-chunked — same model as T3.

### ABAP parser (`server/src/kb/codeparse/abap.ts` new)

- Depends on abaplint (`npm i abaplint` — check: it is a TS library, MIT, usable in Node; if the
  minimal client is heavy, use its stable API `new MemoryFile(filename, code); new Registry().parse`)
- Output model (shared with T3):
  ```ts
  interface AbapObjectChunk {
    id: string;            // `c1`..
    objectType: "class"|"report"|"function"|"include"|"form"
    devName: string;       // object name e.g. ZCL_FI_DELIVERY
    devclass: string | null;
    system: string | null; // e.g. ADT system id
    text: string;          // the unit source (verbatim)
    path: string;          // `<devclass>/<devName>[/<method>]` — downstream `RefinementChunk.path`
  }
  ```
- Walk the abaplint AST/statement list: for a CLASS, emit one chunk per METHOD (body inclusive);
  for report, one chunk per FORM or the report body if no forms; for FUNCTION (function group), one
  chunk per FUNCTION; for INCLUDE constants, one chunk per include.
- Do NOT emit the whole file if a method is huge (>maybe 400 lines): fall back to one chunk with the
  whole method (chunks can be long; retrieval still works — larger = fewer boundaries = safer than a
  random split). Verify with fixture.
- `path` keeps `devclass/object/method` hierarchy so RAG recovers context like heading_path does.

### Enrichment (LLM, T2 helper, optional)

- For each object (not per method — cheaper): one call, `reasoning.effort=none`, prompt with the
  object source (truncated if enormous — use the class summary incl. method signatures only), ask:
  - 1-3 sentence business summary
  - object type (class/function/report/interface) + purpose (e.g. "posts FI docs", "RAP BO access")
  - list of SELECT tables (or DATA/declared tables)
  - list of CALL FUNCTION/FUNCTION names + CALL METHOD + PERFORM forms
  - key parameters if function module
- Output JSON mapped to the existing enrich/summary/frontmatter + `relations` (edges toward
  referenced objects as `uses:` / `reads_table:` roles in the existing relations contract).

### Storage

- Chunks stored via the shared code store (T3 `storeCodeOutput` or equivalent): `chunks.json` +
  wiki page per object (title = object devName, body verbatim source, frontmatter
  {type: abap-object, devclass, system, summary}); Neo4j Document+Chunk + relations as above.
- QA path unchanged — the RefinementChunk shape is equal.

## Test fixtures

Create `server/test/fixtures/abap/` with:
- `zcl_fi_delivery.clas.abap` — a small class (constructor + save + post) with `METHOD ... ENDMETHOD`
- `z_report_sample.abap` — a report with inline form (FORM ... ENDFORM)
- `z_function_top.fugr.abap` — a function module (FUNCTION ... ENDFUNCTION) with directives
  (one fixture is enough: parse via abaplint must throw a meaningful error on unsupported syntax
  rather than silently split).
- Test: chunk count == method/form/function count; boundaries fall on END* lines; path includes
  devclass/name; includes preserved.
