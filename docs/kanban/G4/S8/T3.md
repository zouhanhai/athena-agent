## Context (2026-08-20)

The KB now refines normal documents (PDF/docx via docling → markdown → delta contract → local chunks, T1/T2).
A second source family matters to CALEO: **SAP system code & model definitions** — ABAP (class/method),
CDS views, UI5. These are NOT prose and must NOT go through docling: they arrive as source text/DDL and
their semantic boundaries are syntax-guaranteed.

This ticket scopes the **CDS view** sub-channel. Reference scope is SAP's released Group Reporting CDS
views list for S/4HANA Cloud Public Edition (the URL in the ticket title): ~118 Master Data views +
Transaction Data views. These are what a CALEO consultant would ingest first for consolidation/Group
Reporting Q&A.

## Decision (from user discussion, 2026-08-20)

- **Different intake, same downstream**: code source enters via a **code channel** (direct text,
  NOT docling); downstream (wiki, chunks.json, Neo4j, RAG QA) is REUSED as-is.
- **Chunking stays local/deterministic**: LLM does NOT split code. A **CDS DDL parser** (small,
  rule-based) walks the source and emits each entity as one chunk. Why: syntax boundaries
  (`define view ... as select from ... { ... }`) are deterministic; LLM chunk-splitting would be
  non-deterministic, costlier, and riskier for a fixed corpus.
- **LLM (if used) only for enrichment**: per-view 1-paragraph summary, field business meaning,
  entity extraction (tables/annotations) — via the T2 direct-OpenRouter helper (`reasoning.off`,
  timeout + retry), never for chunk boundaries.
- **Preserve plumbing**: `RefinementChunk { id, text, path }` — code chunks use `path` = view name
  (or `dataCategory/technicalName`) instead of markdown heading_path. Storage/retrieval untouched.

## Design

### Intake — code channel

- `POST /api/kb/ingest` gains a source-kind discriminator or a sibling endpoint for code sources:
  - body accepts `{kind: "cds", content: "<CDS source>", filename?}` OR multipart `.cds`/`.json`
    (from SAP pull or pasted from ADT/Search).
  - NO docling, NO PDF parse, NO markdown rearrange — parse directly.
  - Per-existing server patterns: task queue (task id, progress), dedup (sha256 of normalized DDL),
    wiki storage, RAG vector overlay, Neo4j `Document`+`Chunk`.

### Remote acquisition (SAP side) — REQUIRED design hole fill (2026-08-20 user note)

CDS/ABAP/UI5 code lives IN the SAP system (or the frontend repo), NOT on an end-user's disk — **the
user does not upload these; a remote agent pulls them via MCP and feeds athena**. Both sides must be
designed:

**A. Pull side — SAP MCP (the existing abap MCP server; CDS via ADT):**
- An agent session connects to the SAP system through the already-configured **abap MCP** tools
  (`SAPSearch` → find released CDS views / ABAP objects; `SAPRead` → fetch the full object source;
  for CDS views, ADT `SAPRead` returns the DDL source). The agent is the **fetcher**: it walks a
  target list (e.g. the 118 GR views), pulls each object's source text, and packages them.
- Output shape per object: `{ objectType, objectName, devclass, system, sourceText }` (+ optional
  metadata line per object). That is the **lineage**: which system, which package, which release
  envelope — mandatory for trust (see Decision).

**B. Feed side (athena intake):**
- New endpoint `POST /api/kb/ingest/remote` (or extend `/api/kb/ingest` with `source=mcp`):
  body = `{ kind: "cds", objects: [ { object, sourceText, system, devclass, ts, transport? } ] }`.
- It creates ONE ingest task covering the batch: dedup (sha256 per object), per-object chunking via
  the local parser, wiki/RAG/Neo4j storage (same as upload path), and returns a task id.
- The only difference from the upload path is *provenance*: every wiki page / chunk frontmatter
  carries `system`, `devclass`, `transport` so answers can distinguish "current/active" objects.
- **Auth**: the endpoint is agent-to-agent — accepts a machine token (env `ATHENA_AGENT_TOKEN`),
  not an end-user session. The remote agent (which already authenticated to SAP via MCP) presents
  that token.
- **Batch semantics**: the remote pull can be many objects per call; ingesting is idempotent
  (object sha256 unchanged → skip; changed → update chunk set). A periodic re-pull then works as a
  sync, matching T1's local-rebuild model.

### CDS parser (`server/src/kb/codeparse/cds.ts` new)

- Input: source text of one or more CDS entity/interface views (include `@AbapCatalog...` annotation
  header, `define view <name> as select from <table> [associations] as ... { fields }`).
- Output: `CdsView[]` with `{ technicalName, dataCategoryHint, sourceEntityName, fields[], alias/assoc[], rawMembers }`.
- Rules are local: regex/stack scan for `define view|define view entity|as select from|<Table>|<entity>`
  and closing `}`/`};`, collecting the first non-annotation line after `{` as field list; make part of
  chunk text = the full view definition text (annotations + select + fields) — keep it compact.
- Overrides/missing: treat as a `CdsParseWarning` (not a crash); the section still emits with partial
  metadata. No data left behind: the raw view text is always stored even if metadata parsing misses.

### Refinement stage for code

- Reuse the stage structure: no docling→markdown→section split. Instead:
  - **Step 1 (local)**: `parseCdsViews` → chunks (no LLM).
  - **Step 2 (LLM enrichment, optional flag `enrich=true`)**: for each chunk, build a small prompt
    (`VIEW NAME + DDL excerpt`) to OpenAI/OpenRouter directly (the T2 helper) with `reasoning.effort=none`,
    asking for: 1-sentence business summary, whether it is master/transaction/dimension data, which
    fields are key, possible source table tags. Use the returned JSON for `summary`/`frontmatter`
    negotiator only — chunk text never re-written.
  - Default on: enrichment on for the 118-view probe; concurrency 1 (SAP-honest, avoids key blast radius
    — note the 6900 pipeline is sequential by design, keep it).

### Storage

- Chunks: same `chunks.json` + Neo4j `:HAS_CHUNK`; `path` field contains the technical name +
  dataCategory (`I_CnsldtnGLAccountHierarchy`, `I_CnsldtnSubitem_2`), `path` stores `dataCategory/technicalName`
    (e.g. `` master-data/I_CnsldtnSubitem_2``), no heading_path.
- Wiki page: one page per code/chunk-group? — keep the existing model: a whole ingest (one source file =
  one wiki page titled by technical name), body = full DDL text (frontmatter: system, devclass,
  ts, source kind CDS), summary from enrichment.
- RAG QA: same /api/kb/qa path — the KG/hybrid retriever works with the RefinementChunk shape.
