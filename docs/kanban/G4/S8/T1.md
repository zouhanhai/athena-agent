# G4.S8.T1: two-stage stage-2 full-rewrite output is wasteful — switch to delta/extraction contract

## Observed (2026-08-20)

GR (Group-Reporing-SAP-Doc.pdf, 2.4MB / 2.4M chars / 3364 headers) began refining correctly AFTER the
`athena` provider + contextWindow (1.31M) fixes, but the two-stage **stage-2 per-section pass emits the
full rebuilt markdown as the tool-call argument** — which is 10-60k tokens of output even for a ≤1MB
section. With `maxTokens: 8192` the response was silently truncated → `arguments` JSON incomplete →
`refine_document: output does not match the refinement contract` → fallback (0 chunks). Raising
maxTokens to 65536 keeps GR running (current state: refining) but is a band-aid: it doesn't reduce
what the LLM must emit, just gives it more room. A 2.4MB doc's largest section can still exceed any sane
ceiling, and we have seen 11.7k-token outputs in the OpenRouter logs for individual stage-2 calls.

## Root cause: the LLM should never need to re-emit the document it already has

The model input (a section) already contains the full markdown + stage-1 header levels. The LLM "rewrite"
mainly corrects header hierarchy (already known from stage-1), fixes a few local problems, and extracts
entities/relations/keywords/summary/quality. Forcing it to re-emit hundreds of KB of text it read =>
huge output budget, truncation risk, and information-loss risk (a rewritten doc can drop content the
model "forgot", see the header-map annotation discussion in S1 history, 2026-08-09).

## Design: delta/extraction contract (confirmed direction with user 2026-08-20)

Stage-2 (per-section) LLM output becomes:

```jsonc
{
  "summary": "1-2 sentence section/file summary",
  "sections": [ { "title": "...", "summary": "..." } ],
  "frontmatter": { "type": "...", "topic": "..." },
  "entities": [ { "name": "...", "type": "org", "description": "..." } ],
  "relations": [ { "from": "...", "to": "...", "type": "..." } ],
  "keywords": [ "..." ],
  "quality": { "complete": true, "confidence": 0.9, "issues": [], "action": "auto_accept" },
  "patches": [   // OPTIONAL — the only text-level changes a section needs
    { "op": "retitle_heading",   "index": 4, "level": 3 },
    { "op": "replace_paragraph", "index": 12, "text": "..." },
    { "op": "insert_paragraph",  "index": 15, "text": "..." }
  ]
}
```

Athena applies it locally, keeping fidelity:

- `md_final = apply(original_section_md, stage1_header_levels, patches)`
  (patches are optional; absent patches => header re-level is the only structural edit)
- `chunks = splitParagraphSemantic(md_final)` — existing local function (~1200 tokens/paragraph,
  ~100-token overlap, heading_path), NO LLM text generation
- Output to store: `{ markdown: md_final, chunks, entities, relations, keywords, quality, type/topic }`

**Benefits:**
- Stage-2 output: 10-60K tokens -> ~1-5K tokens per section call. `maxTokens: 8192` covers it even on
  the biggest docs. No truncation class of failure.
- No regression risk to document content: original text is preserved; the model only *proposes* edits
  identified by index/location.
- Cheaper + faster two-stage: same input cost, ~90% less output per call.

**Open questions (resolve in implementation):**
- Patch index stability: paragraph index must be defined on the *original* markdown line/paragraph
  numbering so stages can apply reliably. `splitParagraphSemantic` already produces stable chunk ids
  (c1..cN) — reuse those as the reference grid.
- Global merge (G4.S1 T3 two-stage global pass) should now merge only the *extraction* fields
  (summary/entities/relations/keywords/quality/frontmatter) + patch list — it never re-emits markdown.
- json-schema for `patches` needs a `oneOf` (refactor_heading | replace_paragraph | insert_paragraph |
  delete_paragraph). Add strict-mode tests for each op.
