## Context (2026-08-21, review findings after T7)

Two gaps found while reviewing the T3/T4/T5 code channels end-to-end:

**Gap 1 — the graph gets zero code relationships.** All three parsers ALREADY extract
relationship data locally (deterministic, no LLM):

- CDS: `CdsCodeChunk.sourceTables` + `associations` (`server/src/kb/store/code.ts`)
- ABAP: `AbapCodeChunk.dependencies` with `AbapDependencyKind = table_read | call_function | call_form | call_method`
- UI5: `Ui5CodeChunk.references` (`extractUi5References`: OData service URIs, model names, entity-set/CDS-view bindings)

… but all three `storeXxxOutput` throw it away: the returned `RefineOutputRef` hardcodes
`entities: [], relations: []`. The Neo4j ingest (`server/src/kb/store/ingest.ts`) consumes
`ref.entities` (Entity nodes + MENTIONS) and `ref.relations` (RELATION edges) — so code
documents produce chunks + a Document node and NOTHING else.

**Key ingest semantics (verified in ingest.ts):**
- Entity MERGE is GLOBAL by `nameUpper` — cross-document edges join automatically when
  two documents reference the same canonical name.
- Relation edges do `MATCH (a {nameUpper}) MATCH (b {nameUpper}) MERGE (a)-[:REL]->(b)` —
  if an endpoint entity does not exist (in ANY document), the edge is SILENTLY DROPPED.
  → the mapping must emit entities for external targets too (SAP standard tables, called
  FMs, bound CDS views), not only for submitted units.

**Gap 2 — preclassified contradicts T7.** `tasks.ts` hardcodes:
- runCode L1108: `{ category: "source", pagePath: "wiki/cds/...", topic: "cds" }`
- runAbap L1293: `{ category: "source", pagePath: "wiki/code/...", topic: "abap" }`
- runUi5 L1477: `{ category: "source", pagePath: "wiki/code/...", topic: "ui5" }`

`ingestLlmWiki` (ingest.ts L546) uses `preclassified` for the WIKI PAGE frontmatter
(`type: source, topic: cds`) while the Neo4j Document node uses `ref.frontmatter`
(`type: code, topic: code/<system>` after T7) — two sources of truth diverge, and T7's
acceptance criterion #2 (wiki pages under code/<system>) never takes effect end-to-end.
`category: "code"` is valid: `WIKI_CATEGORIES = DOC_TYPES` (llmwiki.ts L108) and T7 added
`code` as the 14th DocType.

## Design

### 1. preclassified fix (tasks.ts, three sites)

Derive from the stored code ref — single source of truth, no duplicated literals:

```ts
const preclassified: WikiClassification = {
  category: "code",
  pagePath: `wiki/${ref.frontmatter.topic}/${fileName}`, // topic = code/<system>
  topic: ref.frontmatter.topic,                          // code/<system>, code/unknown fallback
};
```

### 2. entity/relation mapping (store/code.ts, all three store functions)

Build `entities: RefinementEntity[]` + `relations: RefinementRelation[]` from the parsed
metadata (conform to the exact shapes from the G4.S1 refine contract — check
`server/src/kb/store/` type definitions first):

| Channel | Entities | Relations |
| --- | --- | --- |
| CDS | view (submitted) + every `sourceTables` entry + every `associations[].target` | view `READS_FROM` table; view `ASSOCIATES` target |
| ABAP | unit `devName` (submitted) + every `dependencies[].name` | `table_read`→`READS_FROM`; `call_function`/`call_method`/`call_form`→`CALLS` |
| UI5 | component (submitted) + every `references` target (entity set / CDS view / service) | app unit `BINDS_TO` CDS view / entity set |

Rules:
- Canonical uppercase names (`MARA`, `ZCL_FOO`) for all entity `name` values — this is
  what makes cross-document joins work via the global nameUpper MERGE.
- External targets MUST be emitted as entities (see ingest MATCH semantics above).
- Dedupe entities/relations within one ref. No LLM, no network — pure mapping.

### 3. Tests

- Store-level: per-channel mapping tests (external entities present, canonical casing,
  dedupe, empty-metadata → empty arrays are fine).
- Pipeline-level: preclassified derivation test (code/<system> topic, wiki/code/ pagePath).
- Follow existing test patterns in `server/test/kb/`.
