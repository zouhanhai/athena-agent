## Context (2026-08-21, user requirement after T8/T9/T10)

Today every `type: code` wiki page renders identically: the T7 metadata panel
(system/devclass/transport badges) + generic markdown (hljs highlighting). The DDIC pages
are a static markdown field table; ABAP pages are a unit/method text wall. The structured
metadata that T3/T4/T5/T9 already persist per chunk (`sourceTables`, `associations`,
`dependencies`, `references`, `fields`) never reaches the frontend.

User requirement (verbatim intent): “code 在 llmwiki 前端也可以优化显示对吗 每一种 code 都有
自己的显示器？表结构如何在 wiki 中显示？可以都做。wiki 树里面不是平铺的所有 abap method
都放在一层而是有层次的。”

## Design

### 1. code-meta API (server)

`GET /api/kb/wiki/code-meta?path=<wiki page path>` (employee auth, read-only):

- Resolve the page → its stored `chunks_ref` (the store façades write
  `<CODE_OUTPUT_DIR>/<stem>/chunks.json` next to `markdown.md`; resolve via the existing
  store conventions — e.g. stem from the page file name, or via the Neo4j Document node's
  `mdRef`/documentId if that is cleaner. Pick ONE approach and document it in the route
  comment).
- Return `{ type, topic, system, devclass, transport, chunks }` where `chunks` carries each
  chunk's `id`, `path`, `heading_path` and its parsed metadata object (fields for ddic,
  sourceTables/associations for cds, dependencies for abap, references for ui5).
- 404 when the page is missing or not a code page. Add route tests.

### 2. Per-DocType renderers (web/src/views/WikiView.vue + components)

When `type: code` AND code-meta resolves, dispatch by `frontmatter.topic`'s channel —
detect via the chunk metadata shape (fields → ddic, sourceTables → cds, dependencies →
abap, references → ui5); otherwise fall back to today's markdown rendering:

| Channel | Renderer |
| --- | --- |
| ddic | schema table: 🔑 on key fields, clickable column sort, search box filtering rows, FK cell → link |
| cds | DDL source in a highlight block + chips row for sourceTables / associations |
| abap | unit navigation list (object → methods from `heading_path`) that scrolls to the section |
| ui5 | component/file structure list (controller/view/manifest groupings from chunk paths) |

Keep the T7 metadata panel above whichever renderer runs.

### 3. Cross-links (no dead links)

FK cells and cds chips link to `wiki/code/<system>/<TARGET>.md` **when that page exists**
(check the loaded tree/pages list); otherwise clicking triggers the existing wiki search
with the target name.

### 4. Hierarchical code tree

- Extend `listWikiPages` (server/src/kb/llmwiki.ts L313) to also return the code lineage
  fields (`system`/`devclass`/`transport`) — they are already embedded in each code page's
  frontmatter (written by `renderCodeMarkdown`/`renderDdicMarkdown`); parse them alongside
  type/topic.
- In the topic tree builder (web/src/kb/wiki-tree.ts), pages with `type === "code"` and a
  devclass/component gain one folder level: `code/<system>/<devclass>/<page>`. UI5 uses the
  component namespace as the folder name. Pages without a devclass stay directly under
  `code/<system>/`.
- `attachHeadings` continues to attach the selected page's heading outline; ddic/abap
  heading nodes scroll to the matching renderer section (id-anchor the sections).

### 5. Tests

- Server: code-meta route (happy path, 404s, auth) in server/test/kb/.
- Web (vitest): renderer dispatch per metadata shape; ddic search/sort/FK-link; tree
  devclass grouping (topic tree snapshot with code pages). `npx vitest run` + typecheck.
