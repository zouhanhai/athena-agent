## Context

GDD (git-driven development) is a **generic, agent-agnostic dev-flow protocol** bundled inside the athena
repo but not athena-specific (boundary rule in ADR 0009: dev-flow = GDD, KB/Q&A = athena). This ticket
packages it into a `docs/gdd/` handbook so any team can adopt it on their own repo without athena coupling
(方案 B: code stays in athena, docs make GDD independently adoptable). Must be done AFTER T1 (Workbench
Kanban/Project split) and T2 (spec state machine simplification) so the handbook reflects the final
state machine (no decomposed, ticket-driven in_progress, spec main-issue closed on done).

## Task

**GDD code separation boundary (2026-08-14 decision):**
- **GDD (move into a `gdd/` package)** = sync + protocol + templates + hooks + plugins:
  `server/src/kanban/` (github-sync sync half, scan, schema, status-map, board, git-lock,
  github-feedback, planning, progress, protocol, lifecycle, roles, state-machine, frontmatter),
  `server/scripts/sync-github.ts`, `hooks/post-commit`, `scripts/install-kanban-hook.sh`,
  `opencode-plugin/`, `docs/kanban/templates/`.
- **athena (stays)** = the UI/read layer that reads GitHub directly: `web/src/` (Workbench
  Code/Issues/Project tabs + api/github.ts), `server/src/routes/kanban.ts` + `routes/github.ts`,
  `server/src/github/` (client), `server/src/employees/`.
- **Split shared modules into two files** so each side is clean. The only kanban module used by both is
  `github-sync.ts`: split it → the **sync half** (`createSpecIssue`, `syncSpecStatus`, `specIssueState`,
  ticketState, subTaskProgress used by sync) → GDD; the **read half** (`buildGithubProjectBoard` + the
  helpers the Project tab needs) → athena (keep in `server/src/kanban/` or a new `server/src/github/
  project-board.ts`). Note the local kanban index (kanban-index.json, write-index.ts, index-file) and
  done-commit plugin were already removed in T4.
