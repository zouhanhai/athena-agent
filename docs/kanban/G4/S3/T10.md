# G4.S3.T10 — Wiki edit → RAG re-embed

## Context

A document may contain a VLM image description that mis-reads a word (e.g. an OCR/vision error). The
wiki page is currently **read-only** (WikiView has no save API), and there is **no mechanism** to push a
wiki edit back into the Neo4j chunk text/embedding. So a correction made in the wiki would not be
reflected in RAG retrieval.

Goal: let a user fix the text directly in the wiki, and have the **affected chunk(s) re-embedded** so
RAG retrieves the corrected content.

## Task

1. **Front-end wiki editing** (`web/src/views/WikiView.vue`):
   - Make the wiki page content editable (contenteditable/textarea toggle, or a small editor).
   - Add a **Save** action that PUTs the edited markdown to a backend save API.
   - Show saved/error feedback. Keep the read-only view as the default; editing is opt-in per page.

2. **Backend save API** (`server`): a route to update a wiki page file (write the new markdown to the
   wiki dir + rebuild index as needed). Reuses `wiki-frontmatter` write-through for metadata.

3. **Chunk re-embed** (`server/src/kb/store/ingest.ts` + `tasks.ts`):
   - After a wiki edit is saved, detect which Neo4j chunk(s) correspond to the edited span.
     Simplest robust approach: re-run the affected chunk's embedding + `MERGE` (update `c.text` +
     `c.embedding`) for the changed section/chunk(s).
   - If the edit is localized (a few words), only the affected chunk(s) are re-embedded
     (incremental). If the edit is large, a whole-document re-ingest fallback is acceptable.
   - Reuses the existing embedder (qwen3-embedding) + the per-chunk progress callback from G4.S3.T9.

## Acceptance

- Wiki page editable + save persists to the wiki file.
- Saving re-embeds only the affected chunk(s); retrieval returns the corrected text.
- Incremental by default; whole-doc fallback for large edits.
- Tests: web wiki-edit/save; server save-API + chunk re-embed. Suites green + vue-tsc clean.
