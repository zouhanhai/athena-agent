## Context

Agentic RAG (G4.S3.T7) was implemented — `AgenticRetrievalService`, `createSearchKnowledgeTool`,
`AgenticJudge` (`createAgenticJudge`), `DuckDuckGoWebSearchProvider` — but **never wired into the
production chat agent**. In `server/src/agents/agent.ts`, `createSearchKnowledgeTool(options.agenticRetrieval)`
only registers when `agenticRetrieval` is passed, and neither `AgentManager` nor `buildApp` ever pass one.
So the Athena chat agent has only the 3 llm_wiki tools (`wiki_search`, `wiki_read_page`, `wiki_graph`) and
**NO `search_knowledge`**.

Consequence (observed live): asking "what is caleo" falls back to web, the stored Q&A pair
(`qa_pairs` in Postgres + `QaPair` node in Neo4j) is never reused, and the agent even reports
"MCP not initialized / no search_knowledge access". Term (semantic_mappings) expansion also never
reaches the agentic path because the agentic search is never invoked. Also confirmed:
`AgenticRetrievalService` is only constructed in tests, never in production
(no `new AgenticRetrievalService` in `server/src` outside tests).

## Task

1. **Wire agentic RAG into `server/src/agents/agent.ts` (`createAgent`)**:
   - When `options.agenticRetrieval` is not supplied, build a default `AgenticRetrievalService`:
     - `search`: the KB retrieval search — reuse the retrieval service the app wires
       (`defaultRetrievalService()` in `server/src/app.ts`, or construct a `KnowledgeRetrievalService`
       with the default Neo4j driver + llm_wiki + semantic mappings + QA reference; see the
       `KnowledgeRetrievalService` ctor in `server/src/kb/retrieval.ts`).
     - `judge`: `createAgenticJudge(modelRuntime)` — reuse the `modelRuntime` already created inside `createAgent`.
     - `webSearch`: `new DuckDuckGoWebSearchProvider()`.
     - `topics` / `graph`: from the retrieval service when available.
   - Register `createSearchKnowledgeTool(agenticRetrieval)` so `search_knowledge` is exposed.
   - Best-effort: on wiring failure log and continue without the tool (never crash agent creation).
   - Prefer wiring in `createAgent` over `buildApp` so the judge reuses the existing per-session
     `modelRuntime` and it works for any caller.

2. **Verify the retrieval service exposes what agentic RAG needs**:
   - `KnowledgeRetrievalService` must provide `search`, `topics`, `graph` (or the agentic service
     maps them). Check `server/src/kb/retrieval.ts` for the exact public surface; add
     `topics()` / `graph()` accessors if missing.
   - The retrieval `search` already returns `qaReference` (stored Q&A) — confirmed folded into hits
     by the G4.S3 T10-era fix in `agentic-rag.ts` (`response.qaReference` → hit). Ensure the default
     wiring sets up `qa` + `mappings` on the retrieval service (see `buildApp` at
     `server/src/app.ts` lines ~381–395 which passes `mappings` and `qa: feedback`).

3. **Tests** (`server/test/kb/agentic-rag.test.ts` + a createAgent-level test):
   - `createAgent` (with a fake/stub retrieval or mocked modelRuntime) registers the `search_knowledge` tool.
   - A stored Q&A pair is reused (already covered by the qaReference→hit test; add an end-to-end assertion if cheap).
   - Existing agentic-rag tests keep passing.
