## Background

Knowledge has a lifecycle (LLM Wiki v2): some facts are fresh, others stale. The wiki frontmatter is
the natural place to carry confidence + lifecycle (G4.S3 core).

## Task

1. Extend the wiki page frontmatter schema (ingest/llmwiki frontmatter writer) with:
   - `read_count` (int, times Athena/retrieval read this page)
   - `last_reviewed` (ISO date, last Athena KB review)
   - `confidence` (float 0..1, decays over time)
   - `topic_history` (ordered list of past topics — migration audit trail)
   `created`/`updated` already exist.
2. **Bidirectional sync with RAG (write-through)**: the same lifecycle fields must ALSO be stored on
   the Neo4j `Document` node (it already carries topic/type/summary shared with the wiki frontmatter,
   and links to the wiki via `WikiPage`/`IS_DOCUMENT`).
   - Document node gains `read_count`, `last_reviewed`, `confidence`, `topic_history`.
   - **Build ONE canonical frontmatter-update function** (e.g. `updateWikiFrontmatter(path, patch)`)
     that: (a) writes the new frontmatter to the wiki md on disk, and (b) writes through the change to
     the Neo4j `Document` node (MERGE by the linked documentId). EVERY future frontmatter change —
     KB review (T2), re-curation (T3), feedback (T5), read_count increment (T1), future manual wiki
     editing — MUST go through this single function so wiki + RAG stay in sync.
3. Increment `read_count` via the canonical function on BOTH the wiki frontmatter AND the Document
   node when the retrieval service surfaces the page.
4. TDD: frontmatter writer emits the new fields; the canonical update function writes wiki + mirrors
   the Document node; read_count increments on both via the shared function.
5. Server tests green + typecheck clean.

## Acceptance

- Frontmatter carries the 4 new fields; a single canonical update function keeps wiki frontmatter +
  Neo4j Document node in sync (write-through) for every change; read_count increments on both.
